The route certificate is one of those secrets, and a CSI-synced Secret exists only while a pod that
mounts it is running. The Route is therefore in a later Argo CD sync wave. With plain helm on a
first install, the Route is rejected until the server's pod is up -- run the install again, or
install with route.tls.mode=edge and switch afterwards.

{{- $sa := printf "%s:%s" .Release.Namespace (include "ambari.serviceAccountName" .) }}
  * In-cluster: KDPS -> Configuration -> "Connect with this ServiceAccount" (inClusterServiceAccount).
                KDPS then acts as system:serviceaccount:{{ $sa }}, which this chart grants
                nothing. In each project KDPS deploys to, grant it admin and, on OpenShift,
                monitoring-edit (OPERATIONS.md §2):
                  oc -n <project> create rolebinding kdps-admin --clusterrole=admin \
                    --serviceaccount={{ $sa }}
                  oc -n <project> create rolebinding kdps-monitoring-edit --clusterrole=monitoring-edit \
                    --serviceaccount={{ $sa }}
{{- end }}
  * OpenShift : KDPS -> Configuration -> log in with the API URL and an account that can deploy.
                Stored in the Ambari database, so it survives pod restarts and upgrades.
  * Kubernetes: KDPS -> Configuration -> upload a kubeconfig. That one is a FILE under
                /var/lib/ambari-server, so keep persistence.enabled=true or it is lost with the pod.
